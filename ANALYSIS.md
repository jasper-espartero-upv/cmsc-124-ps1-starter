Python keeps the string length directly, making len() fast, but strings use more memory, especially when there are many short strings. Since strings can’t be changed in place, repeatedly using += can also be slow, so ''.join() is usually better. For arrays, our dt_array and Ada arrays both store the length and starting index and check whether an index is within bounds. This adds a small amount of work for each access, and non-zero starting indexes require an extra calculation. Our arrays also use more memory because each element is a general dt_value instead of a simple integer. For associative arrays, our map uses hashing and linked chains, while Python’s dict uses a more compact hash-table design and keeps insertion order automatically. Python dictionaries are flexible but can use a lot of memory, and resizing can sometimes slow down an insertion. Overall, these differences are most noticeable when working with large amounts of text, big arrays, or large dictionaries.

2. C lets programmers access a union's contents directly without requiring a tag check. This allows for more control and flexibility over memory and performance. However, this also makes it easier to read the wrong value or forget a case, causing bugs that a language like Rust could catch at compile time. This control and flexibility can be useful in low-level programming and other programming contexts that need precise control, but for most applications, compiler-enforced checks are safer and easier to maintain.

3. We could remove the separate insertion-order array and traverse the hash buckets directly when printing the map. This would save memory and simplify insertion and removal, but the output order would depend on the bucket arrangement rather than the order in which keys were added. As a result, the map might print its entries in a different order than the expected output, causing tests to fail. I would not use this design for this problem set because predictable insertion order is required, but we might use it if output order did not matter and saving memory was more important.

4.  The two bugs are basically opposites: access after release means using memory after you’ve already given it back, while a memory leak means keeping memory you no longer need. Access after release is usually more serious because it can cause crashes, corrupt data, leak information, or even be exploited by attackers. A memory leak usually causes problems more slowly by using up more and more memory until the program slows down or crashes. In a long-running server, leaks can become a big problem over time, while access-after-release bugs are dangerous right away. In a short command-line program, memory leaks are usually less serious because the operating system cleans up the memory when the program exits. However, access after release is still dangerous because it can cause incorrect results, crashes, or file corruption even during a short run. Overall, memory leaks get worse the longer a program runs, while access-after-release bugs are dangerous no matter how long the program runs.
